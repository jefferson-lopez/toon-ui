`@toon-ui/react` is the explicit React integration layer.

Use it when you want to own the adapter contract instead of relying on defaults.

## What it owns

- React rendering runtime
- adapter creation
- adapter coverage metadata
- default preset merging
- render helpers for common controls

## Main exports

- `createToonReactAdapter()`
- `createToonAdapter()`
- `mergeToonComponentRegistry()`
- `createToonReactRuntime()`
- `assertToonReactAdapter()`
- `ToonMessage`
- `ToonRenderer`
- `extractToonMarkdown`
- `getToonButtonProps()`
- `getToonInputProps()`
- `getToonTextareaProps()`
- `getToonCheckboxProps()`
- `basicPreset()`
- `useToonAction()`

## Main exports explained

### `createToonReactAdapter()`

Creates the adapter contract that maps ToonUI semantic nodes to your React components.

```tsx
const adapter = createToonReactAdapter({
  level: 'default',
  components: {
    button: MyButton,
  },
});
```

What it does:

- combines your registry with the selected adapter mode
- computes adapter coverage metadata
- validates strict mode when needed

Use it when:

- you want explicit ownership of the React integration

### `createToonAdapter()`

This is just an alias of `createToonReactAdapter()`.

Why it exists:

- shorter API
- cleaner naming in app code

### `mergeToonComponentRegistry()`

Merges multiple partial component registries into one registry.

```tsx
const registry = mergeToonComponentRegistry(defaults, overrides);
```

Use it when:

- your component ownership is split across modules
- you want preset + overrides composition

### `createToonReactRuntime()`

Creates the React runtime.

```tsx
const runtime = createToonReactRuntime({ adapter });
```

What it gives you:

- protocol APIs from core
- parse/validate/extract helpers
- adapter metadata
- layout configuration
- rendering compatibility with `ToonMessage` and `ToonRenderer`

### `assertToonReactAdapter()`

Ensures the adapter is valid.

Important verified behavior:

- if `level === 'strict'` and coverage is incomplete, it throws

Use it when:

- you want to fail fast on incomplete adapter ownership

### `ToonMessage`

High-level component for messages containing prose plus ToonUI blocks.

What it does:

- renders markdown
- renders ToonUI blocks
- uses `extractToonMarkdown()` internally
- delegates structured block rendering to `ToonRenderer`

Use it for the default assistant-message use case.

### `ToonRenderer`

Lower-level renderer for the structured ToonUI content.

What it does:

- wraps rendering with `ToonProvider`
- parses ToonUI blocks
- validates the generated structure
- renders the AST using registered components or fallbacks

Use it when:

- you want direct control over structured rendering
- markdown rendering is handled elsewhere

### `extractToonMarkdown()`

Removes fenced `toon-ui` blocks and returns the remaining markdown text.

Use it when:

- prose and structured UI must be rendered separately

### `getToonButtonProps()`

Returns normalized button props:

- `type`
- `disabled`
- `onClick`

What it handles:

- reply actions
- submit actions
- disabled-state protection

Use it inside custom button components to keep ToonUI behavior correct.

### `getToonInputProps()`

Returns normalized props for input-like fields.

What it handles:

- field id/name
- html input type mapping
- required/disabled/placeholder
- current value normalization
- `onChange` wiring
- numeric input conversion

Use it when replacing default field rendering with your own input component.

### `getToonTextareaProps()`

Same idea as `getToonInputProps()`, but for textarea controls.

Use it when your custom field component renders a `<textarea>`.

### `getToonCheckboxProps()`

Normalized checkbox wiring helper.

Use it when:

- your custom field renders a checkbox
- you want ToonUI value handling to stay correct

### `basicPreset()`

Returns the built-in default registry used by the default adapter path.

Important verified behavior:

- it includes defaults for `text`, `badge`, `button`, `field`, `card`, `confirm`, `form`, `item`, `list`, `alert`, and `table`

Use it when:

- you want a reference implementation
- you want to extend the built-in visual behavior

### `useToonAction()`

Hook that returns:

- `events`
- `messages`

```tsx
const { events, messages } = useToonAction();
```

Use it when a component needs the protocol interaction APIs without manually threading them down through props.

## Practical decision rule

Use:

- `createToonReactAdapter()` to define component ownership
- `createToonReactRuntime()` to build the runtime
- `getToon*Props()` helpers to keep behavior correct in custom controls
- `basicPreset()` when you want defaults as a base
- `useToonAction()` when child components need protocol interaction helpers

## Adapter levels

| Level | Meaning |
|---|---|
| `minimal` | Only the components you register manually |
| `default` | ToonUI defaults plus your overrides |
| `strict` | Full coverage required or runtime throws |

## Recommended adapter pattern

```tsx
import {
  createToonReactAdapter,
  createToonReactRuntime,
  getToonButtonProps,
  type ToonButtonComponentProps,
} from '@toon-ui/react';

function MyButton(props: ToonButtonComponentProps) {
  return <button {...getToonButtonProps(props)}>{props.node.label}</button>;
}

const adapter = createToonReactAdapter({
  level: 'default',
  components: {
    button: MyButton,
  },
});

const runtime = createToonReactRuntime({ adapter });
```

## Why the adapter exists

A raw component map is too weak as a public contract.

The adapter makes ownership explicit:

- what you replace
- what defaults remain
- whether coverage is complete
- which keys are still missing

```ts
console.log(adapter.meta.level);
console.log(adapter.meta.providedKeys);
console.log(adapter.meta.missingKeys);
```

## When to choose this package

Choose `@toon-ui/react` when:

- you already have a design system
- you need strict rendering ownership
- you want to audit component coverage
- you want adapter behavior to be explicit in code review
